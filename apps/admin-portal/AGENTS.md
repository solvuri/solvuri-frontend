## Admin Portal — project notes

- Auth is real: `app/page.tsx` calls `@repo/api-client`'s `login()` against the real test backend (`https://backend-api-test.solvuri.com`, see `.env.local`/`.env.example`). Admin/SuperAdmin accounts always get `requiresOtp: true` back — there's no token until the OTP step (`verifyOtp()`) succeeds; Merchant/Agent logins would get a token immediately but are rejected here since this app is admin-only. `proxy.ts` gates `/dashboard/:path*` on a `solvuri_auth_token` cookie holding the real JWT, decoding it inline (Edge-safe, no `@repo/api-client`/axios import) and checking `AppRole` is `Admin`/`SuperAdmin` — a Merchant/Agent token does not grant access. Log out via the dashboard header's "Log out" button, which calls `clearAuthToken()`.
- `@repo/api-client`'s `createApiClient()` already attaches the JWT (`Authorization: Bearer`) to every request via an interceptor and unwraps the backend's `{success, message, data}` envelope down to just `data` — don't re-implement either of these per-call. Errors surface as a plain `Error(message)` using the backend's real message.
- Only `Clearack` and `POS` are real backend modules. The fictional Safyri/Reservr/Master modules (invented early in this project before real-backend integration began) have been removed entirely — from `apps/web`'s marketing site, this dashboard's nav/settings, and `@repo/types`'/`@repo/data`'s `Tenant.module` union and mock tenant list. `/dashboard/clearrack` ("Clearrack Stores") is still mock-data-only; `/dashboard/pos` ("POS Locations") is wired to real data (see below). Note the pre-existing "Clearrack" (double-R, here and in `apps/web`) vs. the real backend catalog's "Clearack" (single-R) spelling — a known, minor inconsistency, not fixed as part of the module cleanup.
- **`/dashboard` (Global Stats) is wired to real platform revenue data** — `@repo/api-client`'s `payments.ts` (`getRevenueReport`/`listPayments`, base routes `api/solvuri/payments/*`, Solvuri Admin/SuperAdmin only). Deliberately does NOT depend on `GET /api/tenants` for its "Unique Paying Merchants" stat (that endpoint 500s once any tenant has a subscription — see the merchants-page note above) — instead derives it client-side from the distinct `tenantId`s in the payment ledger, which is real, complete, and unaffected by that bug. The 30-day revenue window (`getRevenueReport(..., "day")`) is a fixed default, not user-adjustable yet; a date-range picker is reasonable future work if needed.
- `/dashboard/merchants` is the first page wired to the *real* backend (not `@repo/data` mocks) — it calls `@repo/api-client`'s `registration.ts` functions (`registerTenant`/`setMerchantCategories`/`setMerchantFeatures`/`listTenants`/`listSystemCategories`/`listFeatures`) directly via `adminApi`, following the documented 3-step onboarding sequence exactly (register-tenant → categories → features+pricing). It's additive — the existing mock Clearrack Stores page isn't touched or replaced by this.
- **`/dashboard/merchants`'s directory table has a per-row expandable panel** for M-Pesa online-checkout status (`getMerchantMpesaSettings`/`verifyMpesaSettings`/`setMpesaEnabled` from `@repo/api-client`'s `mpesaSettings.ts`) — click a row to load and show `isVerified`/`isEnabled` via `StatusBadge` (extended with `verified`/`unverified`/`enabled`/`disabled` styles), send a real 1-KES verification push to a test phone number, and toggle enabled (disabled until verified). The merchant submits their own credentials from `apps/clearracks`' `/merchant/settings` page — this admin page only inspects/verifies/enables, matching the real API's role split (`POST .../verify` and `PUT .../enabled` are Solvuri-admin-only; the merchant's own `GET/POST` aren't callable from here).
- **`/dashboard/catalog`** is real CRUD for the shared System Category/Feature catalog (`@repo/api-client`'s `catalog.ts` — `createSystemCategory`/`updateSystemCategory`/`deleteSystemCategory`/`createFeature`/`updateFeature`/`deleteFeature`, all Solvuri Admin/SuperAdmin only). The `monthlyPrice` set here is only the catalog default/reference value shown during onboarding — the price actually billed to a given merchant is set independently on the Merchants page's step 3 (`setMerchantFeatures`) and can differ per merchant. Inline edit-in-place per row, same flat-`useState` convention as the merchants page — no modal library.
- **`/dashboard/pos`** ("POS Locations") is wired to real data: `listTenants(adminApi)` (tolerating the known `GET /api/tenants` 500-bug the same way the Merchants page does) then `getTenantSubscription(adminApi, tenantId)` per tenant (new wrapper in `@repo/api-client`'s `registration.ts`, `GET /api/tenants/{id}/subscription`), filtered to tenants whose subscription has a category named `"POS"` (confirmed exact — see `apps/pos/AGENTS.md`'s note on the feature-name gotcha). There is **no admin bypass for POS's own sales endpoints** (`IsCashier()`-gated, `Merchant`/`MerchantAgent` only, unlike Reports) — so per-sale POS activity can never be shown here; the page states this honestly instead of fabricating a sales table. Summary cards (location count, total monthly revenue) are computed from the real per-tenant subscription data just fetched.
- Shared design tokens (background/surface/foreground/border/ring/radius/fonts) come from `packages/ui/src/styles/solvuri-theme.css`, imported by this app's `globals.css` (same SOLVURI palette as `apps/web`).
- Sidebar navigation uses `@repo/ui`'s `Sidebar` component — don't reintroduce an app-local sidebar; extend the shared one instead. It renders real `next/link`s with active-route highlighting via `usePathname()`, so it's a client component.
- `/dashboard/clearrack` ("Clearrack Stores") is still `@repo/data`'s `useTenants` mock hook, backed by the mock array in `packages/data/src/mock/tenants.ts` — same swap-out-later convention as `apps/clearracks` used before its own real-backend pass. `Tenant` (in `@repo/types`) is this app's operational model for stores/subscriptions; don't confuse it with `apps/web`'s marketing-oriented `ModuleInfo`.
- `/dashboard/settings` (Platform Settings) intentionally lives under `/dashboard` rather than as a standalone `/settings` route, so it inherits the sidebar shell and `proxy.ts`'s existing `/dashboard/:path*` auth matcher for free. Its form fields are local component state only — not persisted anywhere yet.
