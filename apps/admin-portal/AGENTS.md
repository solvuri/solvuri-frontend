## Admin Portal — project notes

- Auth is real: `app/page.tsx` calls `@repo/api-client`'s `login()` against the real test backend (`https://backend-api-test.solvuri.com`, see `.env.local`/`.env.example`). Admin/SuperAdmin accounts always get `requiresOtp: true` back — there's no token until the OTP step (`verifyOtp()`) succeeds; Merchant/Agent logins would get a token immediately but are rejected here since this app is admin-only. `proxy.ts` gates `/dashboard/:path*` on a `solvuri_auth_token` cookie holding the real JWT, decoding it inline (Edge-safe, no `@repo/api-client`/axios import) and checking `AppRole` is `Admin`/`SuperAdmin` — a Merchant/Agent token does not grant access. Log out via the dashboard header's "Log out" button, which calls `clearAuthToken()`.
- `@repo/api-client`'s `createApiClient()` already attaches the JWT (`Authorization: Bearer`) to every request via an interceptor and unwraps the backend's `{success, message, data}` envelope down to just `data` — don't re-implement either of these per-call. Errors surface as a plain `Error(message)` using the backend's real message.
- Only `Clearack` and `POS` are real backend modules. The fictional Safyri/Reservr/Master modules (invented early in this project before real-backend integration began) have been removed entirely — from `apps/web`'s marketing site, this dashboard's nav/settings, and `@repo/types`'/`@repo/data`'s `Tenant.module` union and mock tenant list. `/dashboard/clearack` ("Clearack Stores") and `/dashboard/pos` ("POS Locations") are both wired to real data now (see below). **The former "Clearrack" (double-R) vs. the real backend's "Clearack" (single-R) spelling drift has been fixed** — `apps/clearack` (formerly `apps/clearracks`), this dashboard's `/dashboard/clearack` route (formerly `/dashboard/clearrack`), and every brand mention across `apps/web`/`apps/admin-portal`/`apps/clearack` now consistently use the single-R "Clearack" spelling, matching the real backend's category name exactly.
- **`/dashboard` (Global Stats) is wired to real platform revenue data** — `@repo/api-client`'s `payments.ts` (`getRevenueReport`/`listPayments`, base routes `api/solvuri/payments/*`, Solvuri Admin/SuperAdmin only). Deliberately does NOT depend on `GET /api/tenants` for its "Unique Paying Merchants" stat (that endpoint 500s once any tenant has a subscription — see the merchants-page note below) — instead derives it client-side from the distinct `tenantId`s in the payment ledger, which is real, complete, and unaffected by that bug. The revenue window is now a user-adjustable date-range picker (From/To `Input`s + "Apply Range"/"Last 30 Days" buttons, defaulting to the last 30 days) driving `getRevenueReport(from, to, "day")` — card titles show the actual selected range. `listPayments` has no date-range params in the documented API, so the Recent Payments table and "Unique Paying Merchants" stat below always reflect the full ledger, independent of the picker.
- `/dashboard/merchants` is the first page wired to the *real* backend (not `@repo/data` mocks) — it calls `@repo/api-client`'s `registration.ts` functions (`registerTenant`/`setMerchantCategories`/`setMerchantFeatures`/`listTenants`/`listSystemCategories`/`listFeatures`) directly via `adminApi`, following the documented 3-step onboarding sequence exactly (register-tenant → categories → features+pricing). **Known real-backend bug, not a frontend issue (may since be fixed)**: `GET /api/tenants` was observed returning a bare `500` (no body) once *any* tenant has a subscription attached — confirmed repeatedly via direct `curl`, independent of any frontend code — throughout most of this project's real-backend integration work, then confirmed working again in production (`solvuri-frontend-admin-portal.vercel.app`) without a corresponding frontend change. Whether or not it recurs, this page (and every other page below that calls `listTenants`) surfaces the failure honestly via `Promise.allSettled`/try-catch rather than crashing or hiding it; per-tenant `GET /api/tenants/{id}/subscription` was never affected.
- **`/dashboard/merchants`'s directory table has a per-row expandable panel** for M-Pesa online-checkout status (`getMerchantMpesaSettings`/`verifyMpesaSettings`/`setMpesaEnabled` from `@repo/api-client`'s `mpesaSettings.ts`) — click a row to load and show `isVerified`/`isEnabled` via `StatusBadge` (extended with `verified`/`unverified`/`enabled`/`disabled` styles), send a real 1-KES verification push to a test phone number, and toggle enabled (disabled until verified). The merchant submits their own credentials from `apps/clearack`'s `/merchant/settings` page — this admin page only inspects/verifies/enables, matching the real API's role split (`POST .../verify` and `PUT .../enabled` are Solvuri-admin-only; the merchant's own `GET/POST` aren't callable from here).
- **The same expandable panel also has "Edit Details" and "Override Subscription" actions**, wiring the two Tenant endpoints from the API doc that nothing had used yet: `PUT /api/tenants/{id}` (`updateTenant` — partial update of brand/contact/domain) and `PUT /api/tenants/subscription/{subscriptionId}` (`overrideTenantSubscription` — direct admin correction of status/dates/`isPaid`/`totalPaid`, separate from the payment-driven flow in `payments.ts`). Both wrappers return `void` and the caller refetches (`loadDirectory()`) afterward — the real API doesn't document a response body for either. **The subscription-override form's "Subscription ID" field is manual, not auto-filled**: `TenantSummary.subscription.id` is speculative (added on the assumption every entity in this API exposes its own id, following the doc's convention elsewhere) and hasn't been confirmed against a real `GET /api/tenants` response, since that endpoint has 500'd every time it's been probed so far (see below) — if a tenant's subscription object does come back with an `id` once the bug clears, the field prefills; otherwise the admin types it in.
- **The same panel also has a "Collect Payment" action**, wiring the two subscription-billing endpoints from API doc §1.5 that nothing had used yet: `POST /api/solvuri/payments/stk-push` (`initiateSubscriptionStkPush`) and `POST /api/solvuri/payments/manual` (`logManualPayment`), both in `@repo/api-client`'s `payments.ts`. Before this, an admin could onboard a merchant (creating an `Inactive` subscription) but had no way to actually collect or log that merchant's subscription payment themselves — only the merchant's own self-service top-up (§2.3, not built in this app) existed. STK push polls `GET /api/solvuri/payments/stk-push/status/{checkoutRequestId}` every 4s until `status` leaves `"Pending"`, backing off client-side after 90s — the exact same mechanics as `apps/clearack`'s checkout-status polling, just implemented with a plain `while`/`setTimeout` loop here instead of a react-query hook, matching this page's existing manual-`useState` convention rather than introducing react-query to it. Manual payment logging returns the logged `Payment` row directly (documented response shape, unlike `updateTenant`/`overrideTenantSubscription` above) but the page still calls `loadDirectory()` afterward for consistency. Same manual-subscription-ID caveat as the Override panel above.
- **`/dashboard/users`** is a read-only list of every platform user across every tenant, wiring `GET /api/Auth/users` (`@repo/api-client`'s `auth.ts` → `listPlatformUsers`, Solvuri Admin/SuperAdmin only) — there was no UI anywhere for this before. `tenantId: null` means a platform-level Admin/SuperAdmin account; a non-null value is that Merchant tenant's id (the response doesn't distinguish a `Merchant` owner from their `MerchantAgent`s within that tenant — only `listAgents`, scoped to one merchant at a time, does that). No create/deactivate actions here — the doc doesn't document any mutation endpoint for this list, so this stays read-only rather than inventing one.
- **`/dashboard/catalog`** is real CRUD for the shared System Category/Feature catalog (`@repo/api-client`'s `catalog.ts` — `createSystemCategory`/`updateSystemCategory`/`deleteSystemCategory`/`createFeature`/`updateFeature`/`deleteFeature`, all Solvuri Admin/SuperAdmin only). The `monthlyPrice` set here is only the catalog default/reference value shown during onboarding — the price actually billed to a given merchant is set independently on the Merchants page's step 3 (`setMerchantFeatures`) and can differ per merchant. Inline edit-in-place per row, same flat-`useState` convention as the merchants page — no modal library.
- **`/dashboard/pos`** ("POS Locations") is wired to real data: `listTenants(adminApi)` (tolerating the known `GET /api/tenants` 500-bug the same way the Merchants page does) then `getTenantSubscription(adminApi, tenantId)` per tenant (new wrapper in `@repo/api-client`'s `registration.ts`, `GET /api/tenants/{id}/subscription`), filtered to tenants whose subscription has a category named `"Point of Sale"` (confirmed via a live `GET /api/system-categories` probe — id 1 is `"Clearack"`, id 2 is `"Point of Sale"`; don't confuse this with the *Feature* that must be named exactly `"POS"` for POS endpoints to work at all, see `apps/pos/AGENTS.md`). There is **no admin bypass for POS's own sales endpoints** (`IsCashier()`-gated, `Merchant`/`MerchantAgent` only, unlike Reports) — so per-sale POS activity can never be shown here; the page states this honestly instead of fabricating a sales table. Summary cards (location count, total monthly revenue) are computed from the real per-tenant subscription data just fetched.
- **`/dashboard/clearack`** ("Clearack Stores") is wired to real data the same way as `/dashboard/pos`: `listTenants`/`getTenantSubscription`, filtered to tenants whose subscription has a category named `"Clearack"` (matching the real catalog exactly now — see the spelling-drift note above). There is no admin-accessible order-listing endpoint for Clearack (`GET /api/clearack/orders/{id}` is a single-order lookup scoped to the storefront that placed it, per `apps/clearack/AGENTS.md`) — the page states this honestly rather than fabricating a sales table, same approach as the POS Locations note above.
- **`/dashboard/tenant-requests`** ("Tenant / License Requests") is a real queue of the Super License applications submitted anonymously via `apps/web`'s contact form — wiring `@repo/api-client`'s new `tenantRequests.ts` (`listTenantRequests`, `GET /api/tenant-requests`; `updateTenantRequestStatus`, `PUT /api/tenant-requests/{id}/status`), both Solvuri Admin/SuperAdmin only. A pending row gets Approve/Reject buttons that just flip its `status`; **approving does NOT create the merchant account** — that's still a manual follow-up via the Merchants page's existing 3-step onboarding, matching the API doc's explicit statement that this endpoint doesn't cascade into tenant creation. Same flat-`useState`/table convention as `/dashboard/users`, no modal library.
- `@repo/data`'s `useTenants`/`useTenant` mock hooks, `packages/data/src/mock/tenants.ts`, and `@repo/types`' `Tenant`/`TenantSettings` types have been deleted entirely — this page, their last consumer, moved to real data above, and nothing else in the monorepo referenced them (confirmed via a repo-wide grep before deleting). If you're looking for the operational tenant/store model now, it's `TenantSummary`/`MerchantSubscriptionSummary` in `@repo/api-client`'s `registration.ts`, not a `@repo/types` type.
- Shared design tokens (background/surface/foreground/border/ring/radius/fonts) come from `packages/ui/src/styles/solvuri-theme.css`, imported by this app's `globals.css` (same SOLVURI palette as `apps/web`).
- Sidebar navigation uses `@repo/ui`'s `Sidebar` component — don't reintroduce an app-local sidebar; extend the shared one instead. It renders real `next/link`s with active-route highlighting via `usePathname()`, so it's a client component.
- `/dashboard/settings` (Platform Settings) intentionally lives under `/dashboard` rather than as a standalone `/settings` route, so it inherits the sidebar shell and `proxy.ts`'s existing `/dashboard/:path*` auth matcher for free. Its form fields are local component state only — not persisted anywhere yet.
