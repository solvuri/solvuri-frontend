## ClearRacks — project notes

- This app owns its own cart state (`lib/store.ts`, Zustand + `localStorage` persistence under `clearracks-storage`). Don't move it back into a shared package unless a second app genuinely needs the same cart shape.
- Storefront routes live under `app/storefront/[subdomain]/...` and are reached via `proxy.ts`'s subdomain rewrite (renamed from `middleware.ts` — Next.js 16's non-deprecated convention). It treats any `localhost:<port>` as the root domain, so subdomain routing works whether this app runs on its own dev port (3001) or alongside the others.
- **The storefront is now wired to the real Clearack API** (`https://backend-api-test.solvuri.com`, see `.env.local`/`.env.example`), not `@repo/data`'s mock hooks. `lib/clearackApi.ts` has the real fetch functions + `useQuery` hooks (`useMerchantProducts`, `useMerchantCategories`, `useDeliveryTowns`) and `submitCheckoutRequest`, all built on the existing `clearracksApi` axios instance from `lib/api.ts`. Real product/category types live in `@repo/types`' `clearack.ts` (`ClearackProduct`/`ClearackCategory`/`DeliveryTown`) — deliberately separate from the mock `Product` type, since the real shape has no `rating`/`colors`/`sizes`/`highlights`/`reviews` (those were invented for the old mock apparel catalog and don't exist server-side).
- **Subdomain → merchantId is a hardcoded stand-in**: `lib/merchants.ts`'s `KNOWN_MERCHANTS` map (currently just `{ onestop: 1 }`). The documented API has no anonymous "resolve this domain to a merchantId" endpoint — `GET /api/tenants` requires an authenticated caller, and a storefront visitor is anonymous by design. A real merchant's `domainName` is also a full custom domain (e.g. `onestop.clearack.com`), not a subdomain label under one shared root — reconciling real custom-domain DNS routing with this app's `<subdomain>.clearrack.xyz` scheme is a separate, bigger infra topic, not solved here. An unknown subdomain shows a "Store not found" state rather than guessing.
- **No anonymous order history exists in the real API.** `GET /api/clearack/orders/{id}` requires an authenticated caller scoped to their *own* merchantId — a guest buyer can't look up their own unrelated order. `orders/page.tsx` and `orders/[id]/page.tsx` are honest "not available yet" stubs now, not fabricated data — don't wire them to fake `Order` records again.
- **Checkout now supports both the `/request` fallback and real STK-push `/initiate`.** After Review, the buyer picks "Pay with M-Pesa now" or "Order now, pay on delivery" — there's no anonymous way to know in advance whether a merchant has Online Checkout enabled (the settings-status endpoint is merchant/admin-only), so `/initiate`'s own rejection message is the source of truth if the merchant isn't set up, not a frontend pre-check. Picking M-Pesa shows a polling "check your phone" screen (`useCheckoutStatus` in `lib/clearackApi.ts`, a `useQuery` with `refetchInterval` that stops itself once `paymentStatus` leaves `"Pending"`) with a ~2-minute client-side safety net (the backend already force-resolves stuck transactions around 90s) — not a hard abort, just an escape hatch to "try again or pay on delivery."
- **New merchant-facing settings surface at `app/merchant/**`** (root-domain only, e.g. `clearrack.xyz/merchant/settings`, NOT subdomain-scoped like the storefront) — a real Merchant/MerchantAgent login (`app/merchant/login/page.tsx`, no OTP) lets a merchant submit their own Daraja credentials (`lib/merchantApi.ts`, `app/merchant/(portal)/settings/page.tsx`). Verifying (a real 1-KES test STK push) and enabling are Solvuri-admin-only actions done from `apps/admin-portal`'s merchants page, not here — this page can only submit/view, matching the real API's role split. `proxy.ts` gates `/merchant/*` (except `/merchant/login`) the same way `apps/admin-portal`'s/`apps/pos`'s proxy.ts gate their own auth-required routes — inline Edge-safe JWT decode, `AppRole` ∈ {Merchant, MerchantAgent}. `lib/auth.ts` (JWT-derived `getMerchantId()`) and the 401→`/merchant/login` interceptor in `lib/api.ts` mirror `apps/pos`'s equivalents exactly — same auth pattern, applied to a different app because Mpesa settings are a Clearack concern, not a POS one.
- **`app/merchant/(portal)/agents/page.tsx`** lets a `Merchant` owner register/deactivate/reactivate their own cashier (`MerchantAgent`) logins (`@repo/api-client`'s `registerAgent`/`listAgents`/`deactivateAgent`/`reactivateAgent`, previously written but unused). Owner-only per the real API — a `MerchantAgent` gets a 403 from the backend, so the "Staff" nav link in `app/merchant/(portal)/layout.tsx` only renders when `useCurrentUser().appRole === "Merchant"`, rather than showing a link that always errors for agents.
- **Known real-backend bug: deactivating an agent is effectively irreversible today.** `GET /api/merchants/agents` only returns active agents, and `PUT /api/merchants/agents/{id}/reactivate` returns `"Agent not found"` even called with the correct id right after a successful deactivate (confirmed via direct API calls, not a frontend bug — the request shape matches the documented contract exactly). The UI still renders a "Reactivate" button per the documented behavior, but it will currently always fail server-side. Flagged to the backend team; not worked around here.
- No dedicated single-product anonymous endpoint exists — `product/[productId]/page.tsx` fetches the same full `useMerchantProducts` list the storefront home page uses (React-Query-cached, so no extra network call in practice) and finds the matching id client-side.
- `CartItem.id` (in `lib/store.ts`) is a `number` now, matching real product ids — not a string like the old mock `prod-1` style ids.
- Client Component pages under `app/` receive `params` as a `Promise` in this Next.js version, not a plain object — unwrap it with React's `use(params)`, not `params.foo` directly (the sync-access shim from Next 15 is gone). Got this wrong once already wiring up the product detail page above; double-check any new dynamic route page. `product/[productId]/page.test.tsx` and `orders/[id]/page.test.tsx` are regression tests for exactly this — if a dynamic route page reverts to sync `params` access, those tests fail. When testing a page that calls `use(params)`, wrap the initial `render()` in an awaited `act()` (see either test file) — otherwise the component's initial suspend happens outside what `render()` awaits and the test hangs on the Suspense fallback.
- `pnpm test` here runs `lib/store.test.ts` (cart logic) plus the two dynamic-route regression tests above via Vitest + Testing Library + jsdom (`vitest.config.ts`).
- `Product` types come from `@repo/types` — extend that shared interface rather than hand-rolling a new product shape per component.
- Shared design tokens (background/surface/foreground/border/ring/radius/fonts) come from `packages/ui/src/styles/solvuri-theme.css`'s vocabulary; this app supplies its own ClearRacks brand values in `app/globals.css`, distinct from the SOLVURI palette used by `web`/`admin-portal`.
- `components/navigation/Navbar.tsx`/`Footer.tsx` (the marketing chrome, used by the `(marketing)` layout) are thin wrappers around `@repo/ui`'s shared `Navbar`/`Footer` (`variant="sticky"`) — the actual markup lives in `packages/ui/src/navbar.tsx`/`footer.tsx`'s `StickyNavbar`/`StickyFooter` branches. The storefront's `components/stores/navigation/StoreNavbar.tsx`/`StoreFooter.tsx` are deliberately **not** part of this — they're cart-aware, per-tenant storefront chrome, a different component solving a different problem, and stay local to this app.
