# This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/` before writing any code. Heed deprecation notices.
## POS — project notes

- **The cart is server-authoritative, not local.** `lib/store.ts`'s `useRegister` only remembers `cartId` (persisted, so a page refresh mid-sale doesn't orphan the draft cart) — every add/remove/qty-change/discount is its own call against `POST/PUT/DELETE /api/pos/carts/{cartId}/...` (`lib/posApi.ts`), and the source of truth for "what's in the cart" is always the server response, applied directly to the react-query cache via `queryClient.setQueryData(["pos-cart", merchantId, cartId], ...)` — no separate refetch needed, since every cart mutation endpoint (confirmed by probing the real backend; the API doc gives no example response body for `POST /carts` or `GET /carts/{cartId}`) returns the full updated cart. This replaced the original "accumulate locally, submit once via `POST /api/pos/sale`" design — that one-shot endpoint (and `submitSale()`/`PosSaleInput`/`PosSaleResult`) has been removed from this app entirely in favor of the cart flow's discount + split-payment support.
- **Checkout supports split-tender payments.** `payment/page.tsx` builds a list of payment lines (method + amount, +reference for Mpesa) rather than a single radio selection, and won't let the cashier complete the sale until the tendered total covers the cart's total (mirrors the API's own "payments total must be ≥ cart total" rule). `checkoutCart()`'s response reuses `PosSaleDetail` (same shape as the sales-history detail view) — the receipt page's `payments[]` rendering already handled multiple tenders with no changes needed.
- **Discounts**: only `Percentage`/`FixedAmount` are wired (in `SaleTicket.tsx`) — the API also lists `Coupon`/`Staff` discount types but documents no request shape for either, so they're left out rather than guessed at.
- **Register/till sessions are optional**, matching the documented behavior ("sales work fine with no register session open"). `RegisterHeader.tsx` shows a live status pill (`useCurrentRegisterSession`) linking to `app/register/[subdomain]/(register)/session/page.tsx`, which handles opening (float + notes), cash-in/cash-out, a live reconciliation preview, and closing (counted cash → expected-vs-actual variance). `GET /api/pos/register/current` 404s with `"No open register session"` when none is open — `fetchCurrentRegisterSession` treats any failure from that specific call as `null` rather than a real error, since that's the only documented non-success case for this endpoint.
- **Real auth, real POS API.** Unlike `apps/clearack` (fully anonymous), *every* POS endpoint requires an authenticated `Merchant` or `MerchantAgent` caller. `app/register/[subdomain]/login/page.tsx` calls `@repo/api-client`'s `login()` (no OTP branch needed — Merchant/MerchantAgent skip 2FA; an Admin/SuperAdmin account logging in here is rejected as "not a cashier account"). `proxy.ts` merges an inline Edge-safe JWT-decode auth gate into its existing subdomain rewrite — same approach as `apps/admin-portal`'s `proxy.ts`, gating on `AppRole` ∈ {`Merchant`, `MerchantAgent`}. The gate is skipped only for `/login` itself.
- **`merchantId` comes from the logged-in cashier's own JWT claim** (`lib/auth.ts`'s `getMerchantId()`, wrapping `@repo/api-client`'s `getAuthToken()`/`decodeToken()`), not from the subdomain — there's no anonymous domain-lookup problem to solve here like apps/clearack had, since the caller is always authenticated. **This means the subdomain in the URL is cosmetic post-login**: a cashier logging in from `demo.solvuripos.xyz` sees `RegisterHeader`'s "Demo — Register" label, but every API call is scoped to *their own* `merchantId`, which may have nothing to do with "demo". This is a deliberate simplification, not a bug — don't build subdomain/merchant mismatch detection on top of it without a real reason.
- **Backend quirk, not a frontend bug**: `POST /api/pos/sale` (and presumably every other `IsCashier()` endpoint) rejects with `"This merchant is not subscribed to the POS feature."` unless the merchant's subscribed `Feature` is named **exactly** `"POS"` — the catalog's original seed name `"POS Terminal"` failed this check even while `isPaid: true`, and renaming the `SystemCategory` to `"POS"` alone didn't help either. Confirmed via direct `curl` against `POST /api/pos/sale`, isolating it from any frontend code. If POS stops working for a merchant after catalog changes, check the feature's exact name first, not the frontend.
- **No dedicated POS product-list endpoint exists** — `lib/posApi.ts`'s `useCatalogProducts` reuses the same anonymous `GET /api/clearack/products/merchant/{merchantId}` apps/clearack uses, since POS sells the same `Product` table. `PosProduct` (in `@repo/types`' `pos.ts`) is a type alias for `ClearackProduct`, not a duplicate.
- **Product management is wired** (`products/page.tsx` — add/edit/delete + inline category creation), open to both `Merchant` and `MerchantAgent` (no owner gate, unlike Pricing/Reports) — matches the real API's role gate on `/api/clearack/products` and `/api/clearack/categories` exactly. There's no POS-specific product-management endpoint either; this reuses the exact same `@repo/api-client` `products.ts` wrappers (`createProduct`/`updateProduct`/`deleteProduct`/`createCategory`) that `apps/clearack`'s merchant portal uses, via new thin pass-throughs in `lib/posApi.ts` (`createPosProduct`/`updatePosProduct`/`deletePosProduct`/`createPosCategory`) that keep this file's existing explicit-`merchantId`-param convention rather than adopting clearack's implicit-`getMerchantId()`-inside-the-wrapper style. Listing reuses the same `useCatalogProducts`/new `useCategories` (the latter hitting the same anonymous `GET /api/clearack/categories/merchant/{merchantId}` clearack uses) — no separate POS category list exists either. Deliberately doesn't duplicate stock adjustment or the "Inventory Overview" table here — `inventory/page.tsx` already owns ongoing stock-level management for this app; this page is catalog (what exists, its price/description/category/visibility), not stock.
- `SaleLineItem.productId` (in `lib/store.ts`) is a `number` now, matching real product ids — not a string like the old mock `prod-1` ids.
- **All internal navigation must use bare, subdomain-relative paths** (`/payment`, `/sales`, `/login`), never `/register/${subdomain}/...` — `proxy.ts`'s rewrite prepends the subdomain prefix on *every* request that reaches it, including client-side navigations, so a link containing that prefix already would double-prefix and 404. This was a latent bug in the original mock-era code (never caught because it was never click-tested end-to-end in a browser); fixed as part of wiring this to the real backend.
- **A cashier session can expire mid-shift.** `lib/api.ts` adds a local response interceptor on `posApi` that clears the token and redirects to `/login` on a 401 — this has to run *before* `@repo/api-client`'s own interceptor (which replaces `AxiosError` with a plain `Error(message)` for any enveloped failure, discarding `.response.status`), so it's registered and then moved to the front of the handler chain. Deliberately local to this app, not added to the shared `@repo/api-client` package.
- `Sale`/`SaleItem` (the old mock type in `@repo/types`) and `@repo/data`'s `useSales`/`useSale` mock hooks have been deleted entirely — `apps/admin-portal`'s "POS Locations" dashboard page, their only consumer, was rewired to real subscription data, and nothing else in the monorepo referenced them (confirmed via a repo-wide grep before deleting). Real POS shapes live in `@repo/types`' `pos.ts` (`PosSaleSummary`/`PosSaleDetail`/`PosReceipt`/`PosCart`/`PosCartItem`/`PosDiscountInput`/`PosPaymentInput`/`PosRegisterSession`/`PosRegisterReconciliation`) — this app's own `useSales`/`useSale` (in `lib/posApi.ts`) are unrelated real-data hooks that happen to share the same name; don't confuse the two.
- **Reports** (`app/register/[subdomain]/(register)/reports/page.tsx`) and **Inventory** (`.../inventory/page.tsx`) are wired to the real API. Reports is owner-only (`useCurrentUser().appRole === "Merchant"`, both the nav link in `RegisterHeader.tsx` and the page itself gate on this — matches the backend's own owner-only restriction on every `/reports/*` route) and shows sales/profit/tax/top-products/top-customers/cashiers/payment-methods/returns for a selectable date range (defaults to the last 30 days). Inventory is open to both `Merchant` and `MerchantAgent` (matches the backend) and covers stock levels, manual adjustments, supplier returns, stock-batch receiving (create → QR code → separate receive step), and movement history.
- **Several report/inventory field names differ from the API doc's own prose/examples** — confirmed by probing the real backend rather than trusting the doc literally: tax report uses `totalTax` not `taxCollected`; top-products uses `unitsSold` not `quantitySold`; the cashiers report uses `cashierUserId`/`cashierName`/`saleCount` not `agentUserId`/`agentName`/`orderCount`; payment-methods uses `totalAmount` not `amount`; inventory movements use a `transactionType` field, not `reason`. The adjustment `reason` field is freeform text server-side (confirmed by successfully submitting an arbitrary unlisted string) despite the doc's prose implying a fixed set (damage/loss/theft/expired/other) — the UI offers those as a `<select>` for convenience, not because the backend enforces them.
- Barcode/QR generation is still not wired — out of scope for this pass, same honesty-over-completeness approach used throughout this session's real-backend work.
- **Receipt email/SMS is wired** (`lib/posApi.ts`'s `emailReceipt`/`smsReceipt`, `POST /api/pos/sales/{saleId}/receipt/email`/`/receipt/sms`) — a "Send Receipt"/"Resend Receipt" block on both `receipt/page.tsx` (right after completing a sale) and `sales/[id]/page.tsx` (resending for any past sale). No documented response example for either endpoint — typed as `void`, matching the envelope's `data: null` convention already used elsewhere for action-only endpoints (e.g. agent deactivate/reactivate).
- **Formal Stock-Count (cycle count) is wired** (`stock-count/page.tsx` start/scan/complete + history, `stock-count/[id]/page.tsx` read-only detail for a past session), open to both `Merchant` and `MerchantAgent` (matches the real API's `IsCashier()` gate on this controller). Distinct from the already-wired stock-batch receiving flow on the Inventory page — this is auditing what's already on the shelf, not receiving new stock. There's no dedicated "current session" endpoint, so the page finds the in-progress one (if any — only one is allowed per merchant at a time, server-enforced) by filtering `useStockCountHistory`'s own results for `status === "InProgress"`, rather than tracking it separately. **Only the scan endpoint has a documented response example** — start/complete/history/detail are all typed as returning the same `PosStockCountSession` shape by inference from that one example, not individually confirmed via a live probe.
- **Pricing (override + bulk update + history) is wired**, owner-only (`Merchant`, matching the real API's gate on this controller — the nav link and `pricing/page.tsx` itself both check `useCurrentUser().appRole === "Merchant"`). Per-item override lives inline in `SaleTicket.tsx` (an "Override" link next to a cart line's price, only rendered for the owner) via `lib/posApi.ts`'s `overridePrice`; bulk update + change history live on `pricing/page.tsx` via `bulkUpdatePrices`/`fetchPriceHistory`. **`overridePrice`'s response and the entire price-history entry shape are undocumented** — the API doc gives no response example for `POST /pricing/override` or `GET /pricing/history`. Override is typed as returning the updated `PosCart`, by the same reasoning as every other cart-mutation endpoint in this API (create/add/update/remove item, apply/remove discount all return the full cart) — not confirmed via a live probe. `bulkUpdatePrices`'s response IS documented (`{ updatedCount }`).
- **Customers + Loyalty are wired** (`customers/page.tsx` list+create, `customers/[id]/page.tsx` detail+edit+purchase-history+award/redeem, `lib/posApi.ts`'s `fetchCustomers`/`createCustomer`/`fetchCustomer`/`updateCustomer`/`fetchCustomerSales`/`awardLoyalty`) — open to both `Merchant` and `MerchantAgent`, matching the real API's `IsCashier()` gate on this controller. **`PosCustomer` and every one of these endpoints' response shapes are undocumented** — the API doc gives request bodies only, no response examples, for the whole Customers+Loyalty section. The type is inferred from the create request's fields (`name`/`email`/`phone`) plus this API's own id/createdAt convention, plus a `loyaltyPoints` field since that's the entire point of the loyalty endpoint — not confirmed via a live probe. Purchase history (`GET /customers/{id}/sales`) is matched server-side by **phone number string** against `Order.CustomerPhone` (no real foreign key, per the doc's own "Special behavior" note) — a sale rung up with a different or missing phone won't show up here, and the UI says so. Award vs. Redeem in the UI is just a sign flip on the same `points` field (positive = award, negative = redeem, per the doc).
- **Void/refund/exchange are wired** (`sales/[id]/page.tsx`, `lib/posApi.ts`'s `voidSale`/`refundSale`/`exchangeSale`, types in `@repo/types`' `pos.ts`) — a "Sale Actions" panel on the sale-detail page. `POST /api/pos/sales/{saleId}/void` (fully reverses: restocks every line, reverses all payments) is **owner-only** (`Merchant`, gated on `useCurrentUser().appRole`), matching the real API's own restriction — a `MerchantAgent` doesn't see the button at all. Refund (full or per-line partial) and exchange (return lines + new lines in one call) are open to both roles, matching the backend. **Void and refund have no documented response example** — typed as returning `PosSaleDetail` by inference from the controller's own pattern (every other sale-lifecycle mutation returns the updated sale), not confirmed via a live probe; if that assumption is wrong, the page still works correctly since it calls `refetch()` on the `useSale` query afterward rather than trusting the mutation's own return value. Exchange's response IS documented (`{ sale, netAmountDue }`) — a positive `netAmountDue` means the customer owes more, negative means they're owed a refund; the endpoint itself never auto-settles that balance, and neither does this UI — it's just displayed as a note after processing.
- Client Component pages under `app/` receive `params` as a `Promise` in this Next.js version — unwrap with React's `use(params)`, not `params.foo` directly. `sales/[id]/page.test.tsx` is a regression test for this; when testing a page that calls `use(params)`, wrap the initial `render()` in an awaited `act()` or the test hangs on the Suspense fallback.
- Register/payment/receipt/sales pages live under `app/register/[subdomain]/(register)/` (a route group) so the header-bearing layout there doesn't wrap the sibling `login/page.tsx`, which has no header.
- `pnpm test` here runs `lib/store.test.ts` (register cart logic) plus `sales/[id]/page.test.tsx` via Vitest + Testing Library + jsdom.
- Tax is a hardcoded 16% VAT computed ad hoc per page, matching `apps/clearack`'s existing convention — not stored centrally, and not sent to the backend (the real `POST /api/pos/sale` request doesn't take a tax field; the backend computes its own totals from `Product.TaxRate`, so the client-side tax shown before checkout is an estimate, not what's ultimately billed).
- Shared design tokens come from `packages/ui/src/styles/solvuri-theme.css`'s vocabulary, imported by `app/globals.css` (same SOLVURI palette as `apps/web`/`apps/admin-portal` — POS is an internal operator tool, not a customer-facing storefront with its own brand identity like Clearack, so it uses the shared palette rather than an independent one).
- The root route (`/`) is intentionally just a minimal landing page, not a full marketing sub-site like `apps/clearack`'s `(marketing)` route group — `apps/web` is the central marketing hub for all modules including this one.
