# This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/` before writing any code. Heed deprecation notices.
## POS — project notes

- **The cart is server-authoritative, not local.** `lib/store.ts`'s `useRegister` only remembers `cartId` (persisted, so a page refresh mid-sale doesn't orphan the draft cart) — every add/remove/qty-change/discount is its own call against `POST/PUT/DELETE /api/pos/carts/{cartId}/...` (`lib/posApi.ts`), and the source of truth for "what's in the cart" is always the server response, applied directly to the react-query cache via `queryClient.setQueryData(["pos-cart", merchantId, cartId], ...)` — no separate refetch needed, since every cart mutation endpoint (confirmed by probing the real backend; the API doc gives no example response body for `POST /carts` or `GET /carts/{cartId}`) returns the full updated cart. This replaced the original "accumulate locally, submit once via `POST /api/pos/sale`" design — that one-shot endpoint (and `submitSale()`/`PosSaleInput`/`PosSaleResult`) has been removed from this app entirely in favor of the cart flow's discount + split-payment support.
- **Checkout supports split-tender payments.** `payment/page.tsx` builds a list of payment lines (method + amount, +reference for Mpesa) rather than a single radio selection, and won't let the cashier complete the sale until the tendered total covers the cart's total (mirrors the API's own "payments total must be ≥ cart total" rule). `checkoutCart()`'s response reuses `PosSaleDetail` (same shape as the sales-history detail view) — the receipt page's `payments[]` rendering already handled multiple tenders with no changes needed.
- **Discounts**: only `Percentage`/`FixedAmount` are wired (in `SaleTicket.tsx`) — the API also lists `Coupon`/`Staff` discount types but documents no request shape for either, so they're left out rather than guessed at.
- **Register/till sessions are optional**, matching the documented behavior ("sales work fine with no register session open"). `RegisterHeader.tsx` shows a live status pill (`useCurrentRegisterSession`) linking to `app/register/[subdomain]/(register)/session/page.tsx`, which handles opening (float + notes), cash-in/cash-out, a live reconciliation preview, and closing (counted cash → expected-vs-actual variance). `GET /api/pos/register/current` 404s with `"No open register session"` when none is open — `fetchCurrentRegisterSession` treats any failure from that specific call as `null` rather than a real error, since that's the only documented non-success case for this endpoint.
- **Real auth, real POS API.** Unlike `apps/clearracks` (fully anonymous), *every* POS endpoint requires an authenticated `Merchant` or `MerchantAgent` caller. `app/register/[subdomain]/login/page.tsx` calls `@repo/api-client`'s `login()` (no OTP branch needed — Merchant/MerchantAgent skip 2FA; an Admin/SuperAdmin account logging in here is rejected as "not a cashier account"). `proxy.ts` merges an inline Edge-safe JWT-decode auth gate into its existing subdomain rewrite — same approach as `apps/admin-portal`'s `proxy.ts`, gating on `AppRole` ∈ {`Merchant`, `MerchantAgent`}. The gate is skipped only for `/login` itself.
- **`merchantId` comes from the logged-in cashier's own JWT claim** (`lib/auth.ts`'s `getMerchantId()`, wrapping `@repo/api-client`'s `getAuthToken()`/`decodeToken()`), not from the subdomain — there's no anonymous domain-lookup problem to solve here like clearracks had, since the caller is always authenticated. **This means the subdomain in the URL is cosmetic post-login**: a cashier logging in from `demo.solvuripos.xyz` sees `RegisterHeader`'s "Demo — Register" label, but every API call is scoped to *their own* `merchantId`, which may have nothing to do with "demo". This is a deliberate simplification, not a bug — don't build subdomain/merchant mismatch detection on top of it without a real reason.
- **Backend quirk, not a frontend bug**: `POST /api/pos/sale` (and presumably every other `IsCashier()` endpoint) rejects with `"This merchant is not subscribed to the POS feature."` unless the merchant's subscribed `Feature` is named **exactly** `"POS"` — the catalog's original seed name `"POS Terminal"` failed this check even while `isPaid: true`, and renaming the `SystemCategory` to `"POS"` alone didn't help either. Confirmed via direct `curl` against `POST /api/pos/sale`, isolating it from any frontend code. If POS stops working for a merchant after catalog changes, check the feature's exact name first, not the frontend.
- **No dedicated POS product-list endpoint exists** — `lib/posApi.ts`'s `useCatalogProducts` reuses the same anonymous `GET /api/clearack/products/merchant/{merchantId}` clearracks uses, since POS sells the same `Product` table. `PosProduct` (in `@repo/types`' `pos.ts`) is a type alias for `ClearackProduct`, not a duplicate.
- `SaleLineItem.productId` (in `lib/store.ts`) is a `number` now, matching real product ids — not a string like the old mock `prod-1` ids.
- **All internal navigation must use bare, subdomain-relative paths** (`/payment`, `/sales`, `/login`), never `/register/${subdomain}/...` — `proxy.ts`'s rewrite prepends the subdomain prefix on *every* request that reaches it, including client-side navigations, so a link containing that prefix already would double-prefix and 404. This was a latent bug in the original mock-era code (never caught because it was never click-tested end-to-end in a browser); fixed as part of wiring this to the real backend.
- **A cashier session can expire mid-shift.** `lib/api.ts` adds a local response interceptor on `posApi` that clears the token and redirects to `/login` on a 401 — this has to run *before* `@repo/api-client`'s own interceptor (which replaces `AxiosError` with a plain `Error(message)` for any enveloped failure, discarding `.response.status`), so it's registered and then moved to the front of the handler chain. Deliberately local to this app, not added to the shared `@repo/api-client` package.
- `Sale`/`SaleItem` (the old mock type in `@repo/types`) is untouched and still used by `apps/admin-portal`'s mock "POS Locations" dashboard page — don't repurpose it. Real POS shapes live in `@repo/types`' `pos.ts` (`PosSaleSummary`/`PosSaleDetail`/`PosReceipt`/`PosCart`/`PosCartItem`/`PosDiscountInput`/`PosPaymentInput`/`PosRegisterSession`/`PosRegisterReconciliation`).
- **Reports** (`app/register/[subdomain]/(register)/reports/page.tsx`) and **Inventory** (`.../inventory/page.tsx`) are wired to the real API. Reports is owner-only (`useCurrentUser().appRole === "Merchant"`, both the nav link in `RegisterHeader.tsx` and the page itself gate on this — matches the backend's own owner-only restriction on every `/reports/*` route) and shows sales/profit/tax/top-products/top-customers/cashiers/payment-methods/returns for a selectable date range (defaults to the last 30 days). Inventory is open to both `Merchant` and `MerchantAgent` (matches the backend) and covers stock levels, manual adjustments, supplier returns, stock-batch receiving (create → QR code → separate receive step), and movement history.
- **Several report/inventory field names differ from the API doc's own prose/examples** — confirmed by probing the real backend rather than trusting the doc literally: tax report uses `totalTax` not `taxCollected`; top-products uses `unitsSold` not `quantitySold`; the cashiers report uses `cashierUserId`/`cashierName`/`saleCount` not `agentUserId`/`agentName`/`orderCount`; payment-methods uses `totalAmount` not `amount`; inventory movements use a `transactionType` field, not `reason`. The adjustment `reason` field is freeform text server-side (confirmed by successfully submitting an arbitrary unlisted string) despite the doc's prose implying a fixed set (damage/loss/theft/expired/other) — the UI offers those as a `<select>` for convenience, not because the backend enforces them.
- Customers/loyalty, barcode/QR generation, pricing overrides, and void/refund/exchange (all real, documented backend features) are **still not wired** — out of scope for this pass, same honesty-over-completeness approach used throughout this session's real-backend work.
- Client Component pages under `app/` receive `params` as a `Promise` in this Next.js version — unwrap with React's `use(params)`, not `params.foo` directly. `sales/[id]/page.test.tsx` is a regression test for this; when testing a page that calls `use(params)`, wrap the initial `render()` in an awaited `act()` or the test hangs on the Suspense fallback.
- Register/payment/receipt/sales pages live under `app/register/[subdomain]/(register)/` (a route group) so the header-bearing layout there doesn't wrap the sibling `login/page.tsx`, which has no header.
- `pnpm test` here runs `lib/store.test.ts` (register cart logic) plus `sales/[id]/page.test.tsx` via Vitest + Testing Library + jsdom.
- Tax is a hardcoded 16% VAT computed ad hoc per page, matching `apps/clearracks`' existing convention — not stored centrally, and not sent to the backend (the real `POST /api/pos/sale` request doesn't take a tax field; the backend computes its own totals from `Product.TaxRate`, so the client-side tax shown before checkout is an estimate, not what's ultimately billed).
- Shared design tokens come from `packages/ui/src/styles/solvuri-theme.css`'s vocabulary, imported by `app/globals.css` (same SOLVURI palette as `apps/web`/`apps/admin-portal` — POS is an internal operator tool, not a customer-facing storefront with its own brand identity like ClearRack, so it uses the shared palette rather than an independent one).
- The root route (`/`) is intentionally just a minimal landing page, not a full marketing sub-site like `apps/clearracks`' `(marketing)` route group — `apps/web` is the central marketing hub for all modules including this one.
